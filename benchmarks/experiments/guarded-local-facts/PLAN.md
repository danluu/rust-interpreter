# Local-value facts after an already guarded write

The larger parser code-capacity treatment failed its changed-source screen and
is parked. Return to the token bottleneck and the saved guarded-runtime profiles.
This experiment first runs an offline census; it does not execute alternative
native code or establish a performance improvement.

Compare actual resumable, profiled, persistent-register emission of each saved
published function. Reproduce its original code bytes, operation spans, region
boundaries and assertion identities exactly. Preserve saved publication order.
Reject a mismatch rather than substituting equal total size. Alternative staging
uses a cumulative 16 MiB budget; report any declined function separately.

The test-only alternative retains local values after a Store or Copy only when
the active guard proves frame disjointness and its immutable typed plan contains
the exact destination register, PC, width and write role. Do not call the mutable
address query after the write. All writes remain immediate. Unknown/unselected
writes, local overlaps, register replacement/eviction, calls and region boundaries
retain their existing invalidation. Normal VM binaries have no enabled alternative.

Record baseline/alternative forwarded facts by kind, retained-write sites,
additional and lost forwarding, function sizes, exclusions, and operation/flush/
overhead spans. Weight sites by the saved matching region-entry counts. Weighted
static words are not retired instructions or latency: branches, helpers, fault
tails and flushes do not execute uniformly. Keep all categories, not just savings.

Three saved public profiles cover token block boundaries, token exhaustive
partitions, and the existing folded-matching control. No guest runs, new native-code
publication or new samples. Freeze evidence and source, acquire the shared lock
within 45 seconds, require 12 GiB at admission and 8 GiB per command, and use two
Cargo workers. Build and invoke the selected ignored offline test three times.
Only an informative census can justify implementation and correctness tests,
followed by a fresh combined primary screen and all required adoption guards.
