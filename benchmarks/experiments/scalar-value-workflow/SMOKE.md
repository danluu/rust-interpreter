# Scalar ABI screening before the full comparison

The September 11 review correctly asks for one timing result before further
runtime or storage projects. Run token then folded, one cycle each: five real
production edits, unchanged original tests, a cold anchor and a deliberately
wrong edit. This is 15 edited primary commands per case, 21 including controls,
seven independent Cargo checks and 14 executed artifact snapshots. Both tools
use the already qualified identical Cargo wrapper. All other controls and the
staged benchmark assertions are unchanged. No scalar timings preceded this plan.

Advance to the existing full A/A and candidate protocol only if token's median
paired complete-command wall improvement reaches 8% (at least twice the largest
recent 3.9943% token A/A envelope), CPU improves, and folded stays within separate
5% wall and CPU guards. The original full-comparison 10% token target and held-out
requirements still apply; this smoke cannot retain the candidate. A failed
screen stops new emitter work and directs investigation to measured export and
runtime costs. Do not retry the same candidate to cross the screen.

Both fresh histories are admitted together using the completed three-cycle
budget experiment's maximum four-cache footprint, 14 maximum-size snapshots
per case, 20% growth, a 256 MiB metadata reserve and the existing 8 GiB running
floor. No further archive batch is a prerequisite for this screen. This replaces
the full history controller's generic storage estimate only for these short
histories; it changes no performance threshold or correctness check.

Run `python3 benchmarks/experiments/scalar-value-workflow/smoke.py --check`, then
supervise `python3 benchmarks/experiments/scalar-value-workflow/smoke.py` with run
id `scalar-edit-smoke-01`. Preserve every sample and any failure.
