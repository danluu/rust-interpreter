# Rust development engine: five rounds of review

These are design-review summaries using ten distinct personas in each round, five of them contrarian. They record conclusions, objections, and proposed tests. They are analytical lenses, not independent expert testimony or empirical validation. The final architecture is in [the implementation plan](./PLAN.md).

The scope is a general tool for developing large Rust codebases. No particular application defines the architecture. The reported symptom is a JIT with some form of deferred type checking that improved cold compilation but often regressed warm compilation. Its implementation and measurements are unavailable, so causal explanations remain hypotheses.

**Round 1 — Diagnose the cold/warm reversal**

The initial personalities emphasize measurement, compiler reuse, execution latency, large workspaces, and skepticism about the proposed mechanism. They are selected from the initial problem: a successful cold-start optimization that did not translate into a better development loop.

1. **The stopwatch empiricist — patient, literal, suspicious of ambiguous metrics.** “Warm” must distinguish an unchanged rerun, a body edit, an interface edit, a compiler-daemon restart, and a warmed application process. Compilation ending and useful test feedback are different endpoints. Recommendation: record command-to-result latency, deferred compilation stalls, and total CPU for replayed edit sequences. Decision test: a claimed improvement must survive counting compilation after program entry and using the same semantic checks, build profile, and test selection on both sides.

2. **The compiler conservator — pragmatic, respectful of accumulated implementation knowledge.** Reuse rustc's frontend before contemplating another implementation of Rust. Rustc already has query-level incremental machinery; the opportunity is to find where reuse ends or becomes expensive, not to assume every invocation repeats all semantic analysis. Recommendation: separate frontend, monomorphization, machine-code generation, and linking measurements. Decision test: if saved backend time is smaller than the required improvement, a backend-only project cannot meet the objective. [Rustc incremental compilation](https://rustc-dev-guide.rust-lang.org/queries/incremental-compilation-in-detail.html).

3. **The impatient runtime engineer — focused on the first useful interaction.** Demand compilation can avoid generating code never reached during a short test, but repeatedly compiling its startup path defeats that advantage. Recommendation: retain native artifacts across application runs and distinguish first-ever misses from invalidated artifacts. Previous runs should supply a cheap hint about what to prepare, without deciding correctness. Decision test: a second identical invocation should perform no semantic or code-generation work unless an actual dependency changed; loading and freshness checks remain measurable costs.

4. **The workspace mechanic — practical, alert to mundane overhead.** A small edit can trigger compiler invocations in dependent crates, build scripts, metadata loading, and final binary construction. A JIT replaces only some of those steps. Recommendation: instrument the Cargo build graph and its critical path before changing runtime execution. Preserve build-script outputs, dependency artifacts, and host/target distinctions. Decision test: compare an edit near the application entry point with one in a deeply depended-on library, and report both invalidation fan-out and elapsed time. [Cargo timings](https://doc.rust-lang.org/cargo/reference/timings.html).

5. **The type-system steward — cautious, precise about what “checked” means.** Deferred machine-code generation and deferred language validation are separate choices. Rust's borrow checking operates over MIR and enforces properties that are not replaced by executing a few paths successfully. Recommendation: keep ordinary checking as the default contract and cache valid results; make any partial-validation preview a separately specified feature. Decision test: an uncalled function with an ordinary type or borrow error must still reject the selected build when rustc would reject it. [MIR borrow checking](https://rustc-dev-guide.rust-lang.org/borrow-check.html).

6. **Contrarian: the anti-JIT accountant — unimpressed by runtime machinery.** A fast AOT backend plus good artifact reuse may provide nearly the whole benefit with fewer compatibility problems. Recommendation: make incremental LLVM and incremental Cranelift with suitable platform linkers first-class alternatives, not straw baselines. Decision test: JIT must beat the best applicable AOT configuration on complete edit/test loops. A reduction in reported compilation time that is consumed by runtime stalls does not count.

7. **Contrarian: the cache cynic — distrustful of “just cache it.”** Retaining an artifact is useful only if checking its validity and finding it are cheaper than rebuilding it. Millions of tiny files, whole-workspace hashing, and eager deserialization can consume a warm-build budget. Recommendation: measure hit cost, metadata bytes touched, and object-loading overhead separately. Decision test: cache hits must be substantially cheaper than misses on the actual small-function distribution; a cache that only helps unusually expensive functions needs an admission policy.

8. **Contrarian: the language purist — intolerant of a disguised Rust subset.** An interpreter that omits unsafe code, foreign calls, unwinding, macros, or ordinary test behavior may demonstrate fast startup without supporting large applications. Recommendation: enumerate the intended compatibility envelope early and provide a complete native fallback for unsupported targets. Decision test: representative supported targets run unchanged, including failure paths; unsupported ones are identified before executing an incomplete substitute.

9. **Contrarian: the throughput realist — thinks in test-suite wall time.** Development includes parsers, compression, database setup, and many other compute-heavy activities. A large interpretation slowdown can erase a small compile-time saving. Recommendation: optimize total developer feedback, allowing unchanged code to remain native and selecting native execution for long tests. Decision test: include short tests, long tests, and substantial startup work; measure the crossover where interpreter or JIT overhead loses.

10. **Contrarian: the maintenance economist — skeptical of projects whose prerequisites are another compiler.** A custom type checker, generic VM, loader, debugger, and hot-reload system together create several major projects. Recommendation: identify the smallest experiment that could invalidate the architecture, and require useful intermediate results. Decision test: the initial deliverable improves or accurately diagnoses ordinary AOT workflows before any full interpreter implementation becomes a dependency.

**Round 1 outcome.** The central candidate becomes persistent, correct reuse with an optional demand-execution layer. Five unresolved problems determine the next round's personalities: cache identity, semantic invalidation, cross-crate propagation, compiler-session lifetime, and background-work costs. No claim about the colleague's exact failure is established.

**Round 2 — Make reuse sound and cheap**

The personalities now specialize in the five unresolved problems, with contrarians looking for ways persistence could preserve the wrong result or add more work than it saves.

1. **The database custodian — meticulous about identities and versioning.** Separate logical item identity from the version of its implementation. Store immutable artifacts and publish a manifest for each validated program revision. Recommendation: a native artifact records its code-generation inputs, symbolic relocations, layout/ABI assumptions, and configuration, not a process address. Decision test: restarting the service and changing load addresses must preserve correct execution; reverting an edit should recover the earlier valid artifact without compiling it again.

2. **The dependency cartographer — methodical about distinguishing kinds of change.** A function body edit can leave its callers' machine code usable, whereas a layout change, embedded constant, or inlined body can invalidate those callers. Recommendation: record the actual compiler dependencies behind each artifact and preserve separate validation, code-generation, and binding dependencies. Decision test: a private scalar body edit recompiles the changed implementation; changing a consumed constant or layout also invalidates consumers. The optimization is rejected if correctness depends on guessing from source-level visibility.

3. **The compiler-session realist — experienced, wary of convenient API assumptions.** A resident service can own caches without retaining editable rustc contexts. Rustc's typing context and much of its data have arena-bound lifetimes. Recommendation: initially use fresh compilation contexts for changed inputs and export explicitly owned artifacts; treat incremental frontend sessions as a separate compiler-engineering milestone. Decision test: the first daemon experiment measures persistence gains independently of any claim that parsing or type checking survives edits in memory. [Rustc memory management](https://rustc-dev-guide.rust-lang.org/memory.html).

4. **The build-graph diplomat — patient with integration constraints.** Cargo remains authoritative for package resolution, features, generated files, and build commands. A compiler wrapper cannot safely suppress downstream work merely because public signatures appear unchanged. Recommendation: keep conservative Cargo invalidation in the first implementation; reduce downstream overhead inside invoked compiler jobs. Later, change metadata contracts and Cargo scheduling together. Decision test: a workspace-wide reduction in downstream invocations requires compiler-derived evidence, not filesystem timestamps or a hand-built API hash.

5. **The scheduling minimalist — protective of interactive latency.** Persistence encourages background checking, compilation, and cache maintenance, but those tasks compete with foreground tests and the editor. Recommendation: bound concurrency, identify work by source revision, and prioritize required checking and currently demanded code. Decision test: compare a daemon with background work disabled to the same daemon with it enabled, including rapid successive edits. Any stale work still consumes the experiment's CPU budget even if its output is discarded.

6. **Contrarian: the hidden-dependency prosecutor — searches for edits the happy path misses.** Trait-implementation additions can change method selection; `const fn` bodies can change compile-time values; macros can introduce new items; async bodies can change hidden state types. Recommendation: preserve compiler dependency tracking, including queries whose result was an absence or a candidate set. Decision test: edit a distant impl, generated declaration, associated constant, or opaque return implementation and compare against a clean rustc build. Identical visible signatures are insufficient proof of reuse.

7. **Contrarian: the durability skeptic — expects crashes and interrupted writes.** A cache whose last successful index references half-written executable code can turn an ordinary interruption into an execution failure. Recommendation: immutable payloads, checksummed records, atomic manifest publication, and conservative rebuilding on unsupported or damaged entries. Decision test: interrupt writes, evict entries, and reopen under a fresh process. Stale and incomplete generations must never be mistaken for a validated runnable revision; cache loss may cost time but not change program behavior.

8. **Contrarian: the frontend pessimist — assumes codegen was the easy part.** A successful function-code cache may still leave macro expansion, parsing, checking, metadata work, or monomorphization traversal dominating latency. Recommendation: measure the residual after cache hits; explicitly branch the project toward frontend work when that residual prevents success. Decision test: compare the maximum theoretically removable backend/link time with the latency target. Do not justify a new interpreter using time that the interpreter cannot remove.

9. **Contrarian: the storage engineer — skeptical of per-function object files.** Fine-grained invalidation does not require fine-grained filesystem objects. Recommendation: pack immutable records into indexed bundles, load by offset, and keep metadata separately addressable. Begin with coarse artifacts if the compiler cannot yet provide sound finer keys. Decision test: scale the number of small functions and measure lookup, relocation, page faults, and garbage collection. A high hit count is meaningless if every hit causes expensive I/O.

10. **Contrarian: the diagnostics advocate — refuses stale confidence.** A cached executable is not proof that the current sources pass the current compiler's checks. Recommendation: maintain a separate validation record bound to the selected build configuration, toolchain, lint settings, and source revision. Successful execution and full validation need different internal states. Decision test: a broken edit must never silently execute the previous successful revision while presenting it as the current one. Line and macro-span changes must also produce accurate diagnostics.

**Round 2 outcome.** The candidate is a versioned artifact service with fresh application processes, strict validation, and conservative initial invalidation. A persistent, editable rustc frontend is no longer assumed. Runtime boundaries, generic instantiation, unwinding, native compatibility, and whether interpretation is worth its implementation cost become Round 3's priorities.

The current Cranelift JIT documentation directly warns that it can lose to AOT because incremental compilation is absent; it also describes dependency-loading limitations. This supports investigating the failure mode without identifying the colleague's implementation. [Cranelift JIT usage](https://raw.githubusercontent.com/rust-lang/rustc_codegen_cranelift/main/docs/usage.md).

**Round 3 — Make the execution model support real Rust**

The prior round made persistence plausible but left native interoperability and runtime complexity unresolved. The new personalities focus on execution boundaries, generic code, resource lifetime, and compatibility.

1. **The ABI mechanic — exacting about every register and byte.** Cached native code, newly compiled code, and native dependencies need one verified calling and layout convention for the selected toolchain and target. Recommendation: derive layouts and ABI lowering from rustc, preserve relocations symbolically, and reject incompatible artifacts. Decision test: mixed calls cover aggregate returns, trait objects, closures, callbacks, alignment, and zero-sized types. Pinning a compiler is necessary but still requires checking the inputs that determine layout. [Rust ABI guarantees](https://doc.rust-lang.org/reference/items/external-blocks.html#abi).

2. **The generics accountant — economical without treating types as interchangeable.** Generic checking and concrete machine-code instances need separate caches. Recommendation: retain generic semantic results where valid, then cache concrete instances using type/const arguments and the compiler dependencies they consume. Include glue and vtables in the artifact graph. Decision test: new instantiations of an unchanged generic function add only required work, while changes to its body, selected trait implementation, or consumed constants invalidate the appropriate existing artifacts. Native Rust monomorphization is the initial representation. [Monomorphization](https://rustc-dev-guide.rust-lang.org/backend/monomorph.html).

3. **The loader conservator — experienced with how much work “no linker” hides.** A JIT still must resolve symbols, relocate references, initialize data, and register runtime metadata. Recommendation: evaluate existing object loading and lazy-materialization infrastructure before writing a custom loader. Bind a validated revision and permit concurrent first calls to request the same artifact safely. Decision test: test mutually recursive functions, data references to functions, and simultaneous first calls. ORC offers relevant lazy and concurrent materialization components, but adapting them to this Rust artifact format remains engineering work. [LLVM ORC](https://llvm.org/docs/ORCv2.html).

4. **The panic custodian — attentive to failure paths other people omit.** Destructor behavior, `catch_unwind`, async cancellation, and panicking tests are ordinary development requirements. Recommendation: preserve the requested panic strategy and complete unwind support across every executed boundary. Use a whole-target native fallback if the selected backend cannot do so. Decision test: panics unwind through compiled helpers, execute destructors in the right order, and preserve test-harness behavior. Cranelift's documented platform limitations are a gating issue, not permission to switch semantics. [Cranelift support status](https://github.com/rust-lang/rustc_codegen_cranelift#not-yet-supported).

5. **The process-isolation architect — conservative about mutable application state.** Persistent compiler artifacts do not require a persistent application heap. Recommendation: each invocation runs in a fresh process with fresh globals, allocator state, TLS, threads, and I/O handles. Keep code revisions immutable for that process's lifetime. Decision test: repeated tests cannot inherit state from previous runs; a crashing application cannot corrupt the compiler's cache. This avoids making state migration, on-stack replacement, and cross-revision pointer lifetimes prerequisites for faster development.

6. **Contrarian: the interpreter abolitionist — challenges the feature named in the project.** A native miss compiler may be simpler and fast enough. An interpreter adds its own value representation, call bridges, runtime checks, and debugging path. Recommendation: implement cached native execution first; add interpretation only when measured first-use compilation costs justify it. Decision test: compare lowering-plus-interpreting against lowering-plus-baseline-compilation for one-shot functions, including all native/interpreted boundary costs. Delete the interpreter experiment if it does not improve complete workloads.

7. **Contrarian: the cold-branch examiner — deliberately exercises the unanticipated path.** Historical execution coverage does not prove which code is needed next. An error branch can allocate, panic, call FFI, or invoke an unseen generic instance. Recommendation: use prior execution solely for prefetch priorities, and preflight required semantics and compatibility without executing that branch. Decision test: an unexpected branch correctly materializes its code or selects a supported path before execution. No required compile error may be hidden until after external side effects in strict mode.

8. **Contrarian: the representation skeptic — dislikes “one copy of every generic.”** Sharing machine code merely because two types have the same size can be incorrect: they can differ in alignment, valid values, drop behavior, trait selection, and constants. Recommendation: defer dictionary-passing or representation-polymorphic execution until specialization cost is proven dominant. Decision test: any later sharing design must specify operations through explicit layout/drop/trait descriptors and pass differential tests. It must not rely on equating distinct Rust types by their storage footprint.

9. **Contrarian: the profiler's adversary — supplies workloads that defeat warm-up heuristics.** A function called once may contain the program's hottest loop, while a frequently called tiny function may cost almost nothing. Recommendation: avoid call-count-only promotion rules; initially use cached native code and simple target-level policy. Any interpreter tier must account for loop work or support a clearly specified escape to native execution. Decision test: one long loop, many trivial calls, branch changes, and short-lived processes must not repeatedly pay unamortized tiering costs.

10. **Contrarian: the portability operator — judges an architecture by what users can run.** Linux success does not establish macOS or Windows support; assembly, TLS, native libraries, and executable-memory APIs expose different gaps. Recommendation: prove one platform end to end, then validate a second architecture before making broad performance claims. Preserve whole-target AOT execution elsewhere. Decision test: report unsupported-target and fallback rates alongside speedups. Excluding every difficult large project would fail the product goal even if the supported subset benchmarks beautifully.

**Round 3 outcome.** The execution design becomes native-first, with an optional interpreter and no live-state migration. The next uncertainties concern evidence: whether the measured improvement survives real edit sequences, whether cache validation scales, whether short and long workloads need different policies, and whether fallback hides lack of coverage. These determine Round 4's empirical and adversarial personalities.

**Round 4 — Try to falsify the performance claim**

The personalities now act as experimentalists and hostile reviewers. Their task is to distinguish an improvement to ordinary development from a favorable startup demonstration.

1. **The counterfactual experimentalist — disciplined about changing one mechanism at a time.** Benchmark a persistent artifact cache before adding a daemon, a daemon before demand compilation, and demand compilation before interpretation. Recommendation: keep separable switches and compare a small factorial set where mechanisms interact. Decision test: each addition explains a measurable gain after counting its own CPU, memory, serialization, and compatibility costs. If disk persistence accounts for the gain, the report must not attribute it to JIT execution.

2. **The corpus naturalist — interested in diversity rather than one showcase.** Large Rust programs vary in crate structure, generic specialization, generated code, native dependencies, and runtime intensity. Recommendation: choose multiple independently maintained examples across these characteristics, with held-out projects that do not influence tuning. Decision test: report results per workload and per edit category, including unsupported cases. A single large database or editor may illustrate a workload; it must not define the tool's compilation model.

3. **The sequence statistician — thinks in developer sessions, not isolated invocations.** Cold wins and warm losses must be accumulated over realistic sequences. Recommendation: replay edits, reverts, broken edits, target changes, restarts, and branch switches; publish both paired latency distributions and total session time. Decision test: calculate how many warm iterations exhaust the initial cold saving. Warm-up work, cache construction, and speculative compilation cannot be omitted merely because they happen outside the command being highlighted.

4. **The no-op zealot — refuses overhead where nothing changed.** A valid native executable should remain directly runnable after ordinary freshness checks. Recommendation: avoid mandatory compiler-daemon attachment or IR reconstruction on an unchanged rerun. A runner that uses a cached image must measure its loading overhead against normal executable launch. Decision test: instrument the unchanged path and require zero compiler invocations and zero regenerated functions. New runtime arguments must rerun the program, not reuse the previous test result.

5. **The incremental-correctness scientist — expects bugs only visible after a sequence.** Single clean builds do not test an incremental system. Recommendation: for each edited revision, compare acceptance and defined observable behavior with an isolated clean build; instrument which dependencies invalidated. Decision test: run sequences that add/remove impls, alter layouts, change macros, toggle features, edit constants, revert edits, and restart midway. Use compiler UI/incremental suites as infrastructure, supplemented by application-level behavior tests. [Compiletest suites](https://rustc-dev-guide.rust-lang.org/tests/compiletest.html).

6. **Contrarian: the daemon exorcist — protective of laptop memory.** A disk cache plus the OS page cache may provide most reuse without another permanently resident compiler. Recommendation: make the daemon an acceleration layer, never the owner of the only valid copies of expensive artifacts. Decision test: compare fresh-process, disk-warm operation with daemon-warm operation under a fixed total memory budget. If the daemon evicts useful editor or application pages, its isolated latency win does not establish a development benefit.

7. **Contrarian: the validation auditor — checks what happened after `cargo check`.** Some Rust diagnostics only appear during code generation. Recommendation: strict demand execution needs preflight of the selected build's required instantiated code and backend/link requirements, or eager handling of checks that cannot yet be separated. Decision test: late constant-evaluation errors, unsupported assembly, and missing native symbols must not be discovered after application side effects when normal compilation would have rejected the build. This requirement may reduce the cold speedup and must be measured. [Cargo check's documented limitation](https://doc.rust-lang.org/cargo/commands/cargo-check.html).

8. **Contrarian: the test-selection skeptic — dislikes advantages created by changing the question.** Running one filtered test does not necessarily mean the ordinary compiler only generates one test's code. Recommendation: keep the selected target and test command identical in baseline comparisons; identify separate experiments that change test-harness code-generation roots. Decision test: selected-test acceleration must preserve required language validation and correct test discovery. Do not confuse avoiding test execution with eliminating its crate's compilation.

9. **Contrarian: the tail-latency hunter — chooses the slowest plausible next edit.** A good median can conceal occasional workspace-scale invalidation or first-use stalls while application locks are held. Recommendation: inspect p95 latency, worst invalidation categories, and concurrent cache misses; precompile historically demanded code only with bounded speculative work. Decision test: introduce a fresh error path, change a widely used type, and make several threads reach uncached functions simultaneously. No lock cycle may depend on the application progressing while its compilation request is blocked.

10. **Contrarian: the baseline defender — insists the incumbent is competent.** LLVM incremental builds, debug-info choices, and linker selection must be compared fairly. Recommendation: use identical semantic settings, record all configuration, and include both stock and tuned baselines. Test full debug information separately from line tables. Decision test: speedups do not come from turning off overflow checks, changing panic behavior, or comparing a cached JIT against a clean native build. Sccache needs its own comparison because its Rust cache does not compose with ordinary incremental compilation in the assumed way. [Sccache Rust caveats](https://github.com/mozilla/sccache/blob/main/docs/Rust.md).

**Round 4 outcome.** Artifact persistence remains essential; daemon residency becomes conditional. Full-validation parity is strengthened to include late compilation errors, so strict lazy execution requires a separate preflight milestone. Session-level and tail measurements replace cold-start headlines. Round 5's personalities focus on deliverable boundaries, stopping rules, frontend feasibility, and a product that remains useful if JIT is rejected.

**Round 5 — Turn the surviving design into an executable project**

The final personalities are shaped by the previous round's operational and evidence gaps. They establish delivery order, technical boundaries, and conditions under which parts of the proposal should be abandoned.

1. **The release conductor — decisive about useful increments.** The first release should provide measurements and a competent native path; the second should demonstrate reusable artifacts across edits and restarts. Recommendation: let finer invalidation, frontend persistence, demand execution, and interpretation earn their places independently. Decision test: every milestone yields something usable even if later milestones fail. An artifact cache that materially accelerates AOT is a successful result; an interpreter that only improves a clean hello-world demonstration is not.

2. **The frontend surgeon — prefers small, verifiable cuts.** If frontend costs dominate, start at observed invalidation boundaries: item inventories, macro outputs, HIR ownership, metadata, and query-result reconstruction. Recommendation: use compiler-derived summaries that separate ordinary body changes from changes with wider effects. Decision test: a scalar implementation edit preserves unrelated semantic results, but adding a nested impl or changing a macro-generated declaration invalidates broader analysis. Rust permits non-local effects from definitions inside bodies, so a textual body/signature split is insufficient. [Non-local definitions](https://doc.rust-lang.org/rustc/lints/listing/warn-by-default.html#non-local-definitions).

3. **The restrained VM designer — willing to build an interpreter only for a measured niche.** If a miss-execution tier is justified, use compact typed operations with precomputed frame offsets and native-compatible memory rather than a dynamically boxed AST walker. Recommendation: lower from checked Rust IR, cover required drop/control-flow behavior, and reuse native dependencies. Decision test: compare this tier with Cranelift and, if needed, a simpler native emitter. Shared generic interpretation, optimizing JIT, and live state migration remain separate experiments, not assumptions of the initial tier.

4. **The developer-experience editor — values predictable commands and honest output.** Preserve normal Cargo target selection, test arguments, diagnostics, and source locations. Recommendation: expose an explanation for recompilation and one explicit native fallback, while keeping backend details out of routine success output. Decision test: developers can reproduce a failure with the pinned native toolchain and identify the source revision that ran. Native fallback must happen before executing the target, never by automatically replaying an already partially executed program.

5. **The resource governor — calm under contention.** Multiple workspaces and rapid edits require bounded memory, versioned work queues, and durable artifacts. Recommendation: partition by toolchain/configuration, deduplicate compilation requests, and keep runtime processes independent of compiler workers. Decision test: cache eviction, a compiler-worker crash, a canceled request, or another active workspace must not mix revisions or require interrupting unrelated work. Service lifetime and managed-worker cleanup need explicit ownership; spare machine capacity is an optimization opportunity, not a correctness requirement.

6. **Contrarian: the compiler-integration auditor — rejects a daemon described as a magic wrapper.** Existing rustc query caches and arenas are not a general mutable compiler database. Recommendation: distinguish a low-risk backend cache from the deeper work required for reusable frontend snapshots and cross-crate metadata contracts. Decision test: a backend prototype is credited only for the stages it bypasses. If producing its key requires rebuilding all MIR or CLIF, that cost stays in the measured warm path.

7. **Contrarian: the JIT liquidation specialist — happy to remove an expensive feature.** The best supported engine may be incremental AOT for most development sessions. Recommendation: retain a product configuration with no JIT and require demand compilation to beat it after strict preflight and runtime loading. Decision test: if AOT meets the improvement targets and JIT adds only small cold gains with warm regressions, ship the AOT engine and stop the JIT branch. The project's success criterion is development effectiveness, not using a particular execution technique.

8. **Contrarian: the second-compiler opponent — resists an attractive but unbounded rewrite.** An incremental IDE semantic model is useful inspiration, but using it as the sole authority for native execution would require establishing all relevant Rust checking and lowering behavior. Recommendation: keep rustc authoritative and borrow architectural patterns rather than treating rust-analyzer as a ready-made replacement frontend. Decision test: frontend improvements must pass the same selected-program validation suite and preserve diagnostics; no claimed speedup may depend on an unacknowledged language subset. [Rust-analyzer architecture](https://rust-analyzer.github.io/book/contributing/architecture.html).

9. **Contrarian: the investment committee — demands a falsifiable return on engineering time.** A universal speedup cannot be promised before measurements. Recommendation: set stage-specific budgets and quantitative success thresholds before implementation, then reevaluate when a bottleneck moves. Decision test: after caching, stop backend work if the residual frontend floor blocks the target; after a frontend pilot, stop that branch if its maintenance burden exceeds demonstrated benefit. Report a bounded improvement honestly rather than describing a research dependency as a shipping feature.

10. **Contrarian: the reluctant adopter — tests the whole product, including escape routes.** A fast tool that breaks debugging, panicking tests, or routine branch switching will not become the default for a large project. Recommendation: require diagnostic usability, recovery, native fallback, memory limits, and platform coverage in the acceptance gates. Decision test: evaluate held-out projects and complete edit sessions with fallbacks included. A useful final report includes who benefits, who does not, and what evidence would change the execution policy.

**Round 5 outcome.** Build a general incremental compilation-and-execution engine around durable validated artifacts. First establish warm AOT improvements. Pursue frontend and cross-crate invalidation when measurements require them. Add demand native compilation only after validation and compatibility gates; add interpretation only after a separate break-even experiment. Keep ordinary application processes disposable, native execution available, and every performance claim tied to a complete developer workflow.

**Changes made by the contrarian reviews**

| Initial temptation | Final decision | Main reason |
| --- | --- | --- |
| Start by implementing an interpreter | Start with measurement and reusable native artifacts | The warm bottleneck may be elsewhere |
| Keep everything in a daemon | Make disk persistence fundamental and residency optional | Restarts and memory pressure must preserve value |
| Cache by function source text | Track compiler-derived semantic and codegen dependencies | Layouts, impls, constants, and macros can change meaning |
| Treat `cargo check` success as enough | Preserve late checks or use eager native compilation | Some errors occur only during code generation |
| Preserve the running application between edits | Start a fresh process per invocation | Avoid heap, TLS, future, and stack migration requirements |
| Assume a backend solves frontend latency | Make frontend work an explicit, separately gated branch | Backend hits can leave most warm costs intact |
| Present supported-only speedups | Include fallback and unsupported rates | General usefulness requires meaningful coverage |

Source documents were checked on September 8, 2026. Recommendations and decision tests are proposed engineering work; no prototype benchmark was executed for this review.
