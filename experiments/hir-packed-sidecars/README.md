# Packed HIR sidecars — source proposal only

This candidate replaces one incremental-session file per eligible HIR body with one bounded pack per capture/reuse policy. The source proposal is based on exact compiler `7efc0d9484da82cd327deb3b48616f8ec81eaf8d`; it does not include the options-hash or single-Walk candidates. It has not been compiled, adopted or benchmarked. The original compiler checkout and installed runtime remain unchanged.

The motivation is the retained Ruff profile: selected cache-on compilation hard-linked 1,414 incremental files versus 3 off, and session preparation self time was 0.383906 versus 0.000954 s. These are one instrumented continued comparison, not a prediction of pack speedup. The full result is in `results/runtime-ruff-hir-self-profile-01`.

`artifacts-01` preserves the first uncompiled proposal, including its source-review error (`lctx` instead of `context` in the replay function) and the original geometric read buffer. `artifacts-02` corrects the receiver, allocates from the opened descriptor's bounded exact length, checks a one-byte overflow, and adds create/partial-write failure controls. `prepare_02.py` binds all 28 full closure files to the new acyclic source identity. `verify_02.py` rechecks unchanged proof-bearing sources and the exact patch with read-only `git apply --check`. These checks establish source integrity and patch application only, not Rust compilation or behavior.

The raw-byte cache is constructed with, and owns, the exact `IncrCompSession` directory. It has no global/TLS map, no arena/HIR value and no cached successful validation. A session-local mutex serializes raw byte/index updates; returned immutable `Arc<[u8]>` data is decoded and checked by the original record codec on every lookup. The existing complete key, format, checksum, normalized entry, current tree, journal, materialization, recapture and poststate checks remain. Capture-only and reuse-enabled policies keep separate packs. Their stable owner IDs select entries, while the exact complete record key still decides validity.

Cold captures queue already checked encoded bytes. Repeated bodies do not rewrite the pack. The sole production finalization call occurs inside `finalize_session_directory`, after its no-errors assertion and before the directory rename/unlock; no Drop implementation publishes anything. This covers ordinary linker completion and the exporter's explicit demand-cache finalization. Callback Stop paths that do not finalize remain unpublished. An all-hit session does not rewrite its inherited pack. A write uses a create-new temporary inode and closes it before replacing the inherited pack; it never appends through a shared hardlink. Failed creation/write/rename retains the inherited destination and compilation continues with ordinary semantics.

The per-body capture line now describes acceptance of validated pending evidence, not durable disk publication. Under incremental-info, successful-session finalization emits a separate exact line:

```
[hir-body-storage] pack=hir-body-capture-v2-cold-materialization-1.pack publication=published
```

The other permitted filename is `hir-body-reuse-v2-ready-hit-1.pack`; the other status is `unavailable`. No line is emitted for an unchanged pack. New-tool diagnostic grammar bindings must explicitly admit this producer-defined line while retaining raw bytes. `incr_comp_publish_hir_body_cache` is a separate finalization span.

The pack framing is eight-byte magic/version `RHIRPK01`, little-endian u32 count, then strictly increasing 32-byte lowercase-hex owner IDs, little-endian u32 record lengths and unchanged JSON record bytes. Duplicate/out-of-order IDs, bad framing/version, nonhex IDs, truncation, trailing bytes and oversized records/packs are misses. Limits are 4 MiB per record, 256 MiB per policy pack and 65,536 entries. No limit is chosen from a benchmark's actual body count. Old inactive owners remain bounded by those limits; a refused new record loses an optimization opportunity and cannot skip ordinary lowering. Corrupt inherited packs start as empty pending caches and are replaced only after successful compilation.

Payload accounting is explicit: two retained policies contain at most 512 MiB of serialized record bytes; loading one policy can temporarily add one exact-length buffer of at most 256 MiB, overlapping that policy's decoded Arc records. Thus payload buffers alone can approach 768 MiB, plus at most 131,072 Arc headers and BTreeMap entries, their allocation/alignment overhead, the current at-most-4-MiB encoded insertion and normal compiler/JSON decoding memory. The format limits bound entry count and payload; they are not a hard RSS guarantee or a claim of a 256 MiB process peak. The source qualifier must measure actual peak before any adoption; no allocation-credit assumption is made. The exact-length allocation uses `try_reserve_exact`, not geometric read-to-end growth.

Current Unix reads use `O_NOFOLLOW` on the opened pack and bounded descriptor metadata/content; other platforms retain ordinary-file checks before and after opening. Every decoded record still requires its full checksum/key and semantic preflight. New filenames do not interpret old loose JSON files as packs. Existing loose files may add one or more migration sessions' copy cost; no deletion or copy-filter shortcut is included. Performance comparisons require fresh independent histories.

See `QUALIFICATION.md` for unrun control requirements. No compiler or application workload is authorized by this source packet.
