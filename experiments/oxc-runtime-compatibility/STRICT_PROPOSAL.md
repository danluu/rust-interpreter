# Proposed strict Oxc qualification

This is an unrun source proposal. Repeat the complete existing 16-call history with both `--trap-unsupported-calls` and `--run-try-callbacks` absent. Keep the same three tests, six source states, full library-test crate, profiles, default features, compiler/tool/std identities, MIR level 3, cache-off settings, two jobs, JIT settings and resource limits. No compiler, launcher, application or test change is proposed.

The ordinary launcher rejects `--run-try-callbacks` without trapping (`RROOT/scripts/interpreter.py:331`). The exact published exporter source also rejects this combination (`crates/mir-export/src/main.rs:427`). Therefore dropping only the trap flag is not a valid strict invocation.

All 16 admitted diagnostic artifacts have empty unavailable-call lists, but this does not establish strict lowering. At the published source checkpoint `185efda9403389fcb408100e5765306179be2cbe`, `lower.rs:2025` selects `try_callback` before unavailable-call trapping. `lower/tls.rs:5` emits the normal-return callback call without recording an unavailable site; it does not implement catching/unwinding. A strict run can therefore reveal a `catch_unwind` lowering failure even when the previous call report was empty. Such a failure must remain a failure, with the complete source restored and diagnostic compatibility qualified only at its previously stated scope.

The exact published `main.rs`, `lower.rs` and `lower/tls.rs` were read from that Git checkpoint and independently matched against the build-02 source freeze. Retained read-only source review is `.work/oxc-runtime-strict-source-review-01/source-review.json`, SHA-256 `94d7c260c397edb7266ad0e5618501374f308ea1e0e3079db041f39b0459a278`. The current exporter checkout's `lower.rs` has later edits, so the review uses the admitted Git blob rather than its current contents.

Proposed isolated outputs are `.work/oxc-runtime-strict-compatibility-01`, fresh `cache/interpreter` and `cache/jit` subdirectories, and `oxc-runtime-strict-compatibility-01:<engine>` namespaces. Preserve the completed diagnostic cache/evidence and all published runtime/source bytes. Reuse the acquired R-owned source only through the same reviewed source-edit/restoration context; no transfer or registry update is needed.

The exact order remains original interpreter/JIT batches, wrong-prefix negatives separately for each of the three tests in each engine, each of the three cumulative production refactors in interpreter/JIT, then the restored original in interpreter/JIT. That is ten successful batch calls and six individual expected assertion failures. Never drop a test, change its expectations or reinstate diagnostic flags after a strict failure. No selective retry is proposed.

The minimal successor controller should preserve the existing timing and process boundaries and change only its fixed output/namespace/policy, remove the two flags, and validate the strict receipt contract:

- Require the ordinary launch report to state `trap_unsupported_calls=false` and `run_try_callbacks=false`. Its tool/runtime/std and compiler flags must remain the admitted identities.
- Require absence of `rust-interp-unavailable:` output and absence of call-report path/list fields. The exporter writes `.calls.json` only when trapping is enabled (`main.rs:155`); an absent file is expected and must not be converted into a synthetic empty report. Fresh strict caches prevent stale trap sidecars; reject an unexpected sidecar for the selected artifact.
- Retain the selected crate's actual dep-info file on every call, binding it to the selected `.rmeta.rbc` filename and the recorded compiler invocation. The exporter registers both policy variables and entry selections in `env_depinfo` (`main.rs:202`). Require exactly one unset `# env-dep:RUST_INTERP_TRAP_UNSUPPORTED_CALLS` and unset `# env-dep:RUST_INTERP_RUN_TRY_CALLBACKS`, with no assigned form. Also verify the exact single or batch test selection in that file. This verifies the exporter observed the absent variables, beyond simply trusting the requested flags.
- Preserve the batch entry catalog, exact bytecode hash, single fresh selected test-crate invocation, all six guest assertions, strip/loader rejection, frozen inputs, source and registry guards, full runtime/std/tool/provider checks, and final restoration checks. Compiler failure is not an expected negative assertion.

The source-proven ordinary launcher clears inherited `RUST_INTERP_*` variables before constructing Cargo's environment and only adds these options when explicitly selected (`interpreter.py:509–529`). The new freeze must continue binding the complete small Cargo configuration and explicit environment; it must not introduce a project-config override of either policy or `RUST_INTERP_DEMAND_BODIES`.

Capacity and scheduling remain canonical lock with 600-second admission, 24 GiB entry, 9 GiB stop, 8 GiB supervisor floor, 12 GiB cache bound and 2 GiB evidence bound. The completed diagnostic history allocated about 2.88 GB of cache. At this proposal's read-only check, free space was 24,764,424,192 bytes, below the 25,769,803,776-byte entry gate. Do not lower the gate or clear unrelated work. Preparation can proceed; execution must retain a concrete admission/capacity failure if the gate is still unmet. No cleanup action is part of this proposal.

Next step after source-plan review: implement a separate strict successor and preparer, bind the actual published tool key and complete prior evidence, freeze exact source/plan/launch, and request root review of that concrete launch. No new build, compiler probe, launcher execution or benchmark was performed for this proposal. Success would qualify these selected tests and edits without either opt-in lowering policy; it would not establish general Rust support, full Oxc compatibility or performance under 0.5 seconds.
