# Proc-macro span-handle lookup candidate

This is one single-file prototype against compiler `58e1e1f5311f4424ea81def4763081f6da62d9b3`. The eleven inspected bridge/server files are byte-identical to public base `cea272fa356e94bd2ee2cadf376630aa0683867a`; their hashes are in `source-review.json`. The exact patched handle module compiled standalone with the pinned public compiler and passed four container controls. No active compiler source or package was changed, and no full compiler build, bridge integration test, benchmark or holdout ran. No performance improvement is established. The initial source-only review remains recorded in `source-review.json`; its original proposal bytes are retained in the control archive.

The candidate replaces only the reverse numeric-handle lookup inside `InternedStore` with the existing `FxHashMap`. The value-to-handle interner remains unchanged. The general `OwnedStore` used for token streams remains a `BTreeMap`, preserving its removal and destructor order. `InternedStore` construction requires `T: Copy + Eq + Hash`; its values cannot have user destructors. Its current sole server use is spans.

The existing bridge has already removed the obvious buffer and thread overhead:

- `library/proc_macro/src/bridge/client.rs:118–132` takes, clears and restores one reusable buffer for requests and responses. `buffer.rs:39–42` clears only the length; capacity survives. `server.rs:124–129` overwrites that same buffer after request decoding. This is ownership transfer, not a new byte-buffer allocation or full-buffer clone per warm API call.
- `server.rs:216–220` directly invokes the dispatcher closure in the same-thread case. `closure.rs:9–25` supplies a C-compatible function/environment pair without boxing it.
- The serialized C boundary is intentional: `bridge/mod.rs:1–7` permits client and server copies built by different compiler stages with different Rust ABIs. Replacing it with Rust references, trait objects or arbitrary typed Rust values is not a safe same-thread shortcut.
- `server.rs:149–175,195–220` sends nested expansion to the cross-thread path because client symbol state cannot be reentered. The prototype leaves this fallback, TLS borrowing and both panic boundaries untouched.

The remaining candidate seam is concrete. `server.rs:55–64` interns every outgoing span and resolves every incoming span handle. `handle.rs:50–68` currently routes that resolution through `OwnedStore` and its B-tree. Token-tree transport contains spans for identifiers, punctuation and literals, and three spans for each group (`bridge/mod.rs:352–389`; `rustc_expand/src/proc_macro_server.rs:106–179`). The existing value-to-handle hash table already suppresses duplicate span allocation, but reverse lookups still search a B-tree and unique spans allocate B-tree storage. Hashing numeric handles removes those tree traversals without skipping any compiler API call or macro execution.

The patch retains the global `AtomicU32` counter and relaxed ordering, exact duplicate interning, nonzero check, overflow failure, and missing/stale-handle panic. Numeric handles remain globally allocated and may have arbitrary gaps from nested or concurrent invocations; there is no handle-minus-base indexing assumption. No table iteration affects encoding order. The wire format, C layout, server API and client code do not change. Every filesystem/environment access, tracked dependency operation, diagnostic emission and macro call still executes in the original order. `track_env_var`/`track_path` are unchanged at `rustc_expand/src/proc_macro_server.rs:484–493`.

The saved self-profile for selected unit 56462 records 966 `expand_proc_macro` invocations totaling 391.138496 ms. That event includes macro user code and all bridge/server work and has no handle-table attribution. It gives no supported estimate of this candidate's savings. The opportunity is expected constant-time lookup and fewer tree-node allocations, not elimination of macro execution or serialization. Hash-table capacity, allocator behavior, cache locality and adversarial handle spacing could offset any gain; ordinary process memory and end-to-end wall/CPU must be checked. This is not sufficient evidence to schedule a full compiler rebuild ahead of higher-priority measured work.

Four unit controls are included in the patch and passed in the [standalone control run](../../results/proc-macro-span-handle-controls-01/README.md): exact handle/value/counter equivalence against the ordered store with repeated intern values and large counter gaps; rejection of handles from another live or completed store; zero-counter rejection; and unchanged counter-overflow rejection. They do not establish bridge integration correctness. The first supervisor failed only after the tests passed because its output parser omitted libtest's “should panic” label. A separate validation checked the saved outcomes and unchanged source/compiler hashes without recompiling or rerunning the tests; both receipts are preserved.

Before timing or adoption, real proc-macro qualification is still required: span/token round trips, `span-api-tests`, `span-preservation`, `mixed-site-span`, `subspan`, `expand-expr` (including its nested-symbol regression), and panic controls with ordinary same-thread and forced cross-thread execution. A small side-effect fixture should perform ordered environment reads, tracked path reads, file writes and diagnostic emissions around repeated span calls; compare cold/edit/restore output, dep-info, raw diagnostic spans/snippets and native/exported results. Preserve uncalled type/borrow/const rejection. Use a memory-intensive token-tree case and interleaved macro clients to exercise table growth and handle separation. No result caching or changes to application code are needed.

Any eventual experiment needs a separately identified compiler/tool/sysroot and truthful patched rust-src inventory. `compiler/rustc_proc_macro/Cargo.toml:13` points at `library/proc_macro/src/lib.rs`, so this is a compiler-server change as well as a standard-library source change. The frozen production MonoItem compiler/package and its full public/custom library-source equality prerequisite cannot simply be relabeled for this patch. Preserve the old identities and qualify the changed source configuration explicitly; the current proposal does not alter those checks.
